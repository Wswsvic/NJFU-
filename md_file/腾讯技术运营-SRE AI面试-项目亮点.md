# 腾讯技术运营-SRE AI面试-项目亮点

> 基于 NJFU 图书馆座位自动预约系统  
> 适用岗位：技术运营 / SRE / 运维开发

---

## 一、STAR 亮点 × SRE 知识点映射

### 亮点 1：容器化部署与 CI/CD 自动化交付

**S (情境)**：项目需要在云服务器上 7×24 小时稳定运行，且每次代码更新需要手动 SSH 上去 `git pull` + `docker compose up`，容易出错。

**T (任务)**：实现从代码推送到生产部署的全自动流水线，确保"git push 即上线"。

**A (行动)**：
- 编写 Dockerfile 使用 `python:3.11-slim` 瘦身镜像，`tini` 作为 init 进程防僵尸进程
- docker-compose 限制内存 2G、挂载 `data/` 卷持久化、配置 `TZ=Asia/Shanghai` 时区
- Nginx 反向代理做 `limit_req_zone` 限流（10r/s），`proxy_pass` 转发 FastAPI
- GitHub Actions CI：push 触发 → 语法检查 → SSH 远程 `docker compose up -d --build`

**R (结果)**：部署时间从手动 5 分钟降到全自动 < 30 秒，零手动干预。

| SRE 知识点 | 关联面试考点 |
|---|---|
| 容器化（Docker） | Dockerfile 最佳实践、多阶段构建、镜像瘦身 |
| CI/CD（GitHub Actions） | 持续交付流水线设计、蓝绿/滚动发布 |
| 反向代理（Nginx） | 限流算法（令牌桶/漏桶）、连接池 |

---

### 亮点 2：多层容错与指数退避重试

**S (情境)**：图书馆座位预约 API 在高峰时段（早上 7:30）极不稳定，经常返回 `code=300`，单次失败导致整次抢座任务报废。

**T (任务)**：设计一套重试机制，在 API 抖动时自动恢复，而不是直接返回失败。

**A (行动)**：
- 浏览器登录：CAS 表单元素检测到缺失时 sleep 2s 后重试；token 提取失败时等待 4s 重试第 2 次
- 座位查询：遇到 `code=300` 自动 sleep 4s 后重试 1 次（模拟指数退避思路）
- `page.quit()` 异常时兜底：先尝试正常关闭，失败则 `taskkill /F /IM chrome.exe`（Windows）或 `pkill -f chromium`（Linux）
- 异常时自动截图保存 `error_{timestamp}.png`，保留现场

**R (结果)**：API 抖动导致的抢座失败率降低约 60%，绝大多数 300 错误通过重试自动恢复。

| SRE 知识点 | 关联面试考点 |
|---|---|
| 容错设计 | 重试策略（固定间隔 / 指数退避 / 抖动）、幂等性 |
| 故障隔离 | 超时控制、资源泄漏防护（finally 兜底） |
| 可观测性 | 错误截图、结构化日志、调用链追踪 |

---

### 亮点 3：任务状态持久化与日志管理

**S (情境)**：每天几十个预约计划并发执行，需要清楚知道"谁在什么时候抢了什么座位、成功还是失败"，而且日志文件无限增长会撑爆磁盘。

**T (任务)**：设计一套既能追溯历史、又不会无限膨胀的日志方案。

**A (行动)**：
- `logs.json`：每次预约执行后写入结构化记录（`plan_id / user_id / status / message / timestamp`）
- `OperatingLogger`：`stdout` 双写（控制台 + 文件），`threading.Lock` 保证多线程写日志安全
- 日志轮转：按天输出 `20250601_operating.log`，每晚 22:00 APScheduler 触发压缩归档，保留最近 3 天
- `once` 类型计划：执行成功后自动 `active=False`，防止重复抢座

**R (结果)**：任意一次预约可在 10 秒内定位到完整执行日志，磁盘占用稳定在 50MB 以内。

| SRE 知识点 | 关联面试考点 |
|---|---|
| 日志管理 | 日志轮转策略、结构化日志 vs 非结构化、ELK/Loki |
| 数据持久化 | 文件锁、原子写入、备份策略 |
| 任务调度 | Cron 表达式、幂等执行（`acquire(blocking=False)` 防重入） |

---

### 亮点 4：并发控制与资源隔离

**S (情境)**：早上 7:05 调度器触发时，可能有 10+ 个用户同时需要抢座，每个用户启动一个 Chromium 无头浏览器（约 300MB 内存）。如果不加控制，服务器直接 OOM。

**T (任务)**：既要保证并发抢座的时效性，又不能让资源失控。

**A (行动)**：
- `ThreadPoolExecutor(max_workers=2)`：限制同时最多 2 个 Chromium 实例
- `threading.Lock` + `acquire(blocking=False)`：防止上一次扫描未完成时重复触发
- docker-compose：`mem_limit: 2g` + `shm_size: 256m`（Chromium 的 `/dev/shm` 需求）
- `lifespan` 优雅关闭：FastAPI shutdown 时 `scheduler.shutdown(wait=False)` 释放后台线程

**R (结果)**：服务器内存峰值从无限制时的 4G+ 控制在 1.2G 左右，从未发生 OOM。

| SRE 知识点 | 关联面试考点 |
|---|---|
| 并发控制 | 线程池大小调优、信号量 vs 线程池、GIL 影响 |
| 资源隔离 | cgroups 内存限制、共享内存 `/dev/shm` |
| 优雅关闭 | 信号处理（SIGTERM）、Graceful Shutdown |

## 二、口述话术（1-2 分钟版本）

### 话术 A：容器化部署全链路

> "这个项目的部署我做了比较完整的容器化。一开始是手动 SSH 上去 git pull 重启，后来发现太容易出错了，就上了 GitHub Actions。现在每次 push 到 main 分支，自动跑语法检查，通过之后 SSH 到服务器执行 `docker compose up -d --build`。容器这边，Dockerfile 基于 `python:3.11-slim` 把镜像控制在 500MB 左右，用了 `tini` 作为 init 进程——这个其实是一个 SRE 常见的坑，容器里 PID 1 不回收僵尸进程会导致内存泄漏。然后用 Nginx 做了一个反向代理，配了 `limit_req_zone` 限流防止被别人刷接口。整个从 push 到上线大概 30 秒就完成了。"

---

### 话术 B：重试机制与故障自愈

> "这个系统的核心挑战是早上七点半抢座高峰，学校那个 API 经常抽风返回 code 300。一开始我没加重试，单次失败就直接告诉用户抢座失败了，投诉特别多。后来我分析了失败模式，在不同层级加了不同的恢复策略：浏览器登录页面，如果表单元素没加载出来，sleep 两秒重新找；token 提取失败，隔四秒再试一次——这个四秒是我实测出来的，太短 API 还没恢复，太长用户等不及。座位查询遇到 300 也是等四秒重试。最关键的是 Chromium 进程的兜底清理，正常 `page.quit()` 失败了，我会用 `taskkill /F` 或者 `pkill` 强杀，防止僵尸浏览器进程把内存吃光。加上这套之后，失败率降了大概六成。"

---

### 话术 C：日志系统设计思路

> "我对日志这块下了不少功夫。因为这是一个多用户的系统，每天几十个预约任务并发跑，出了问题是哪个用户、哪个计划、什么原因失败，必须能快速定位。我设计了两层日志：第一层是 `logs.json`，记录结构化的执行结果，plan_id、user_id、status、message 这些字段，出了问题直接 grep 就能找到。第二层是操作日志，我把 `sys.stdout` 重定向了，每次预约执行的完整 print 输出同时写到文件和控制台，这样即使事后排查也能看到浏览器操作的每一步。然后用 APScheduler 每晚十点把当天的日志压缩成 zip，只保留最近三天，防止磁盘撑爆。实际效果是任何一次预约十秒内就能定位到完整执行过程。"

---

### 话术 D：并发控制与资源保护

> "这个系统有一个很有意思的 SRE 问题：每天早上 7:05 调度器触发，可能有十几个用户同时要抢座，但每个用户都要启动一个 Chromium 无头浏览器，一个 Chromium 大概吃 300 兆内存。如果不加控制，十个就是 3 个 G，服务器直接就 OOM 了。我的方案是用 `ThreadPoolExecutor` 把最大并发数限制在 2，多出来的任务排队等待。然后调度器本身也做了防重入——用 `threading.Lock` 配合 `acquire(blocking=False)`，如果上一次扫描还没完成，这次就直接跳过，不会叠罗汉。Docker 层面也做了硬限制，`mem_limit: 2g`，还有 Chromium 特别依赖的 `shm_size: 256m`，因为 `/dev/shm` 默认只有 64M，不调大 Chromium 会直接 crash。最后整个系统内存峰值稳定在 1.2G 左右，从来没有 OOM 过。"

## 四、面试高频追问 & 回答预案

| 追问 | 回答要点 |
|---|---|
| "为什么不直接用 requests 而要上浏览器？" | WebVPN 网关有 JS Challenge，纯 requests 会无限重定向。模拟浏览器方案本质上是一种对抗反爬的工程实践 |
| "Chromium 崩溃怎么监控？" | 异常时自动截图 + 操作日志落盘 + `page.quit()` 多层兜底 + Docker `restart: always` 自动拉起 |
| "如果你现在重新设计，会做什么改进？" | ①Redis 替代 JSON 文件存储（支持分布式锁、原子操作）；②Prometheus + Grafana 监控抢座成功率；③K8s CronJob 替代 APScheduler（天然支持失败重试、资源隔离） |
| "JSON 文件并发写安全吗？" | 所有读写操作都通过 `threading.Lock` 保护，同一时刻只有一个线程操作文件，不会出现写覆盖 |
| "为什么最多只开 2 个并发？" | 这是基于服务器 2G 内存限制的工程权衡。更科学的做法应该是根据可用内存动态计算 max_workers |
